# 福礼社卡（福卡）模块实施计划

## Context

用户需要类似京东卡的福卡能力：充值、商城消费和送礼。现有消费者端已有登录、下单、微信支付模拟、订单与退款入口；Mock 已有内存订单/支付流水，数据库文档已有 `acc_account`、`acc_account_flow` 和福利卡支付渠道设计。

本次在现有 Taro 消费者端与 Express Mock 内完成端到端演示，不新增 CloudBase 数据库、不修改真实 SQL、不接真实资金。首版范围：每用户一个福卡余额账户、模拟充值、福卡全额支付、向已注册用户转赠、原路退款和收支流水。不做卡号卡密、绑卡、分享领取、混合支付及真实支付上线。

## 正确性契约

### Safety：绝不能发生

1. 余额不得为负；所有金额在福卡 API 和账本中使用整数分，满足 `balance = totalIncome - totalExpense`。
2. 每笔余额变化必须有流水，且 `balanceAfter = balanceBefore ± amount`；无半笔转赠、无订单已扣款但无流水。
3. `${userId}:${requestId}` 唯一标识一次用户操作并保存参数摘要；同键同参数返回首次结果，同键不同参数返回冲突，不得重复执行。
4. 订单支付额外以 `orderNo` 去重，退款以原支付单去重；即使更换请求号，也不得重复扣款或退款。
5. 转赠必须同时产生转出和转入流水，双方余额总和不变；禁止自己转给自己、收款人不存在、超额转赠。
6. 福卡接口只采用 JWT 中的用户身份，不信任请求体中的余额属主 `userId`；不能跨用户查询或操作账户。
7. 不维护独立的浏览器本地余额账本，避免 Mock 与本地余额分叉。

### Liveness：最终必须发生

1. 模拟充值只有在明确的 Mock 支付确认后才入账；重复确认保持成功且不再次入账。
2. 已受理的充值、转赠、福卡支付和退款，在 Mock 进程存活期间可通过原 `requestId` 查询结果。
3. 余额不足或业务校验失败时，订单保持待支付、账户不变，可充值后继续支付或改用模拟微信支付。
4. 福卡订单退款完成后，订单状态、支付记录、退款记录和福卡收入流水均可通过业务单号关联。

### Unknown outcome 与恢复

- 超时、断网、丢响应均视为“结果未知”，不能等同于扣款失败。
- 写请求不自动换新请求号重试；页面保留并按操作类型持久化当前请求号，先查询原操作结果，再展示成功或允许明确业务失败后的新操作。
- Mock 重启会清空内存账本，这是演示限制；不承诺崩溃恢复或生产持久化。真实服务需数据库事务、条件更新/行锁和唯一约束，本次不宣称已具备。

## 模型边界与实现步骤

### 1. 类型与福卡服务

修改 `src/types/index.ts`，新增福卡账户、流水、充值结果、转赠结果和操作结果类型；`Order` 补充可选 `payMethod/payTime`，`PaymentResult` 补充支付状态字段。

新增 `src/services/fuli-card.ts`：

- 封装 `GET /fuli-card/account`、`GET /fuli-card/flows`、`GET /fuli-card/operations/:requestId`。
- 封装 `POST /fuli-card/recharge`、`POST /fuli-card/recharge/complete`、`POST /fuli-card/transfer`。
- 提供请求号生成与暂存；网络异常后用原请求号查询，不自动重放扣款。
- 复用 `src/services/api.ts` 的 token、响应包络和错误处理；账户、流水、操作查询均禁用前端缓存。

### 2. Mock 账本与路由

扩展 `frontend/admin/mock/seed-extra.cjs`，增加并导出福卡账户、流水、充值单、转赠单和操作结果数组；账户按用户懒创建，初始余额为零。

新增 `frontend/admin/mock/fuli-card-service.cjs`，集中实现：

- 账户查询、流水分页、充值创建/确认、转赠、订单扣款、订单退款、操作查询。
- 先完整校验，再在单个无 `await` 的同步提交段修改账本；请求摘要、业务唯一键与余额不变量集中检查。
- 充值确认、订单支付和退款分别按业务单号去重，不能只依赖 `requestId`。
- 提供不变量校验函数，供每次资金变更及自动化验证调用。

新增 `frontend/admin/mock/routes-fuli-card.cjs` 并在 `frontend/admin/mock-server.cjs` 注册。使用现有 JWT/SECRET_KEY 验证当前用户，沿用 `ok/fail/paginate/fmt`，返回稳定业务错误信息。

修改 `frontend/admin/mock/routes-trade.cjs`：

- `/api/pay/create` 在现有微信支付逻辑前增加 `fuli_card` 分支：校验订单归属和待支付状态，全额扣款后写入支付渠道 3；不触发微信回调。
- 已支付订单重复请求返回首次支付结果，不新增支付或消费流水。
- `/api/pay/refund` 对福卡支付执行一次性余额退回，订单使用现有已退款状态约定；微信支付路径不变。
- 保留原下单逻辑，不为本功能重写库存、优惠券或订单模块。

修改 `frontend/admin/mock/perf.cjs`：福卡账户/流水/操作结果和订单查询跳过短 TTL 响应缓存，防止充值、转赠、支付后读取旧余额或旧订单。

### 3. 消费者页面与交易集成

新增单页模块 `src/pages/card/index.tsx`、`index.config.ts`、`index.module.scss`：

- 福卡余额卡片、累计收支和“模拟资金”标识。
- 预设充值金额与自定义金额；充值创建和模拟确认期间防连点，明确展示处理中/结果确认中。
- 送礼表单：已注册账号、金额、祝福语；展示收款人校验、余额不足和自转限制。
- 收支流水展示类型、金额、变动后余额、业务单号、对方和时间；无流水时展示空状态。

修改 `src/app.config.ts` 注册 `pages/card/index`。修改 `src/pages/mine/index.tsx` 及样式，增加福卡余额与充值/送礼入口；未登录或加载失败显示对应状态，不能伪造为 0。

修改 `src/pages/checkout/index.tsx` 及样式：

- 支付方式增加“福礼社卡”，显示当前余额和差额；已知余额不足时提示先充值，服务端仍做最终校验。
- 调用扩展后的 `payOrder(order, 'fuli_card')`；微信路径保持默认，避免影响已有调用方。

修改 `src/services/trade.ts`：

- `payOrder(order, method = 'wechat')` 增加福卡分支，使用稳定的 `ORDER_PAY:${orderNo}` 请求号；福卡支付不调用 `/pay/wechat/notify`。
- 福卡网络异常通过操作查询恢复结果，不直接二次扣款。
- `refundOrder` 对服务端福卡订单调用退款接口；本地订单和其他模拟订单保持原逻辑。

修改 `src/pages/order/index.tsx` 及样式：待付款订单可选择模拟微信或福卡继续支付，展示福卡支付标识；退款后刷新订单与余额，不把结果未知显示成明确失败。

## 反例日志与设计修正

| 反例 | 设计修正 |
| --- | --- |
| 直接复用当前 `/pay/create` 会在未扣福卡余额时把订单标记已支付 | 福卡分支先完成账本扣款，再提交订单支付状态 |
| 丢响应后生成新请求号会重复充值或转赠 | 持久化原请求号，先查询操作结果；订单另按 `orderNo` 去重 |
| 浏览器本地兜底余额与 Mock 各自变化 | 福卡不建立本地资金账本，服务不可用时明确提示 |
| 账户 GET 命中缓存导致支付后仍显示旧余额 | 福卡和订单查询跳过前后端缓存 |
| 只修改订单为已退款但不退余额 | 福卡退款同步写收入流水和退款记录，并按原支付单幂等 |
| 转给不存在用户时沿用卡券模块的随意兜底用户 | 收款人必须精确匹配，失败前不改变任何账户 |

## 代码到模型映射与验证

### 自动化验证

扩展 `frontend/admin/mock/verify.cjs`，使用隔离账本夹具运行：

1. 充值创建、重复确认、并发重复请求只入账一次；同请求号不同金额返回冲突。
2. 正常转赠双方各一条流水且总余额守恒；不存在收款人、自转、余额不足均无余额/流水变化。
3. 福卡订单重复支付（含更换请求号）只扣一次；两笔订单竞争同一余额时不能透支。
4. 福卡退款和重复退款只退回一次，订单、支付、退款和流水引用完整。
5. 每个场景后检查余额非负、累计收支等式、流水前后余额连续和业务单号唯一。
6. 用固定种子生成有界操作序列，混合重复、乱序确认和非法操作，记录失败种子及操作轨迹以便复现；进程重启持久化和真实数据库崩溃恢复明确不在本轮验证范围。

运行 `node frontend/admin/mock/verify.cjs`，同时保证已有商品、订单、退款及视频检查继续通过。

### 浏览器端到端验收

1. 按既有预览约束重启 Mock 与 `preview-server.js`，通过账号 `zhangsan / 123456` 登录，确保存在真实 Mock JWT。
2. 我的 → 福礼社卡，充值 200 元；确认只有支付确认后余额才增加，重复操作不增加流水。
3. 向 `user1` 转赠 20 元，张三余额为 180 元；切换 `user1 / 123456` 后余额为 20 元，双方流水共享转赠单号。
4. 验证不存在账号、自转、超额转赠均提示明确错误且余额不变。
5. 张三购买不超过 180 元的商品并选择福卡，确认订单已支付、余额精确减少，订单号/支付号/消费流水一致。
6. 创建超过余额的订单，确认福卡支付被拒绝且订单待支付；再验证微信继续支付路径不受影响。
7. 对已支付福卡订单申请退款，确认只退回一次且余额恢复；刷新后账户和流水不读取旧缓存。
8. 检查网站/H5 布局、按钮防连点、空流水和加载失败状态。所有页面和提示均明确为模拟资金，不宣称真实充值或支付已上线。

### 运行时对账计划

Mock 在资金操作后执行不变量检查，日志记录 `requestId`、业务单号和流水号但不记录 token。真实服务接入时，将同一不变量转为定时对账：账户余额与流水汇总一致、支付单与消费流水一一对应、转赠双边流水成对、退款不超过原消费；异常进入人工核查，不能自动二次扣款补偿。
