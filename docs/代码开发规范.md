# 福礼社平台 · 代码开发规范与重构评估

> 适用对象：参与管理后台、H5、小程序与 Mock API 开发的前后端同学。
> 目标：保证多人协作下的一致性、可回归、可演进；同时给出是否需要重构的结论与路线。

## 1. 技术栈与目录

```
福礼社平台/
├─ mock-server.cjs            # Mock API 入口（Express，端口 8080）
├─ mock/                      # 内存数据、服务层、路由、回归脚本
│  ├─ seed.cjs                # 基础种子（租户/用户/商品/SKU/角色菜单）
│  ├─ seed-extra.cjs          # 扩展种子（订单/退款/采购/结算/发票/菜单）
│  ├─ helpers.cjs             # ok/fail/paginate/like/numEq/fmt
│  ├─ authz.cjs               # 鉴权、权限、数据范围
│  ├─ *-service.cjs           # 业务服务（stock/fund/distribution/promotion/invoice/finance）
│  ├─ routes-*.cjs            # 路由分组
│  └─ verify*.cjs             # 回归脚本
├─ frontend/admin/            # 管理端 Vue3 + Element Plus（3100）
├─ frontend/h5/               # H5 Vue3 + Vant（3001）
├─ frontend/miniapp/          # Taro 小程序
└─ docs/                      # 手册、评审、术语表、验收标准
```

## 2. Mock API 分层规范

### 2.1 分层职责
| 层 | 职责 | 禁止 |
| --- | --- | --- |
| `seed*.cjs` | 声明内存数据与初始状态 | 写业务逻辑、读请求 |
| `*-service.cjs` | 领域规则、状态机、金额计算、幂等 | 直接读写 `req/res` |
| `routes-*.cjs` | 鉴权、参数校验、调用 service、返回响应 | 复制业务规则、直接改多张表 |
| `helpers.cjs` | 通用响应/分页/比较 | 引入业务状态 |

### 2.2 响应与错误
- 成功：`ok(res, data, message?)` → `{ code: 200, message, data }`。
- 失败：`fail(res, message, status)` → HTTP 与业务码一致（400/401/403/404）。
- 禁止在路由中 `res.status(500)` 裸返回；未知异常统一兜底并保留可读信息。
- 业务错误优先抛带 `status` 的 `Error`，由路由统一转换（参考 `invoice-service.cjs`）。

### 2.3 分页与筛选
- 入参统一兼容 `current/size` 与 `pageNum/pageSize`。
- 返回 `{ records, total, current/pageNum, size/pageSize }`。
- 筛选参数为空串/null 时视为不过滤（使用 `numEq`）。
- 模糊查询统一用 `like()`，避免 `includes(undefined)`。

### 2.4 鉴权与数据隔离
- 所有非公开接口先 `authenticate`。
- 功能权限用 `requirePermission('xxx')`，菜单权限码与 `menuPermissions` 保持一致。
- 行级隔离必须使用 `scopeMerchant / scopeSupplier / scopeOrders / assertMerchantAccess`，不得手写 `if`。
- 越权统一 `forbidden(res, ...)` → 403；禁止把越权数据“过滤后返回”而不报错（除非接口语义就是列表裁剪）。

### 2.5 金额、状态与幂等
- 资金一律以“分”存储（`fundService.toCents`），展示层转元并保留两位。
- 状态码集中定义，不允许魔法数字散落；新增状态必须同步术语表、验收标准、回归断言。
- 状态机必须显式校验“当前值 + 1”，禁止跳步。
- 支付回调、退款审核、入库、开票、分账必须按业务主键幂等（订单号/退款单号/采购单号）。

### 2.6 命名
- 文件名：`kebab-case`（`routes-trade.cjs`、`finance-service.cjs`）。
- 变量/函数：`camelCase`；常量：`UPPER_SNAKE_CASE`。
- 布尔：`is/has/can` 前缀；金额字段带 `Amount`，费率带 `Rate/rateBp`。
- 路由：资源复数 + 动作，如 `/api/admin/invoice/:id/red-flush`。

## 3. 前端规范（管理端 / H5）

### 3.1 组件与目录
- 管理端页面放 `src/views/<模块>/<页面>/index.vue`；路由 `component` 与菜单 `component` 保持一致。
- H5 页面放 `src/views/<模块>/index.vue`，路由懒加载。
- 通用逻辑抽 `src/utils`、`src/config.ts`，禁止在页面里硬编码域名/端口。

### 3.2 请求与状态
- 统一使用 `@/utils/request`，不在组件内直接用 axios/fetch。
- 接口失败由 request 统一提示；页面只处理业务分支，避免重复 toast。
- 列表页统一维护 `loading / tableData / pagination / searchForm` 四件套。
- 金额展示统一 `formatMoney`；禁止直接拼接浮点数。

### 3.3 权限与体验
- 路由 `meta.permission` 与后端权限码一致；按钮级权限按需用 `v-if` 控制。
- 写操作二次确认；危险操作使用 `ElMessageBox.confirm/prompt`。
- 空态、loading、错误态三态齐全；表格列宽与 `fixed` 操作列保持可用。
- H5 适配安全区与底部导航，图片懒加载。

### 3.4 样式
- 使用 `scoped`；设计变量集中在全局样式，禁止页面内定义重复主题色。
- 类名采用 `block-element` 语义，不写无意义缩写。

## 4. 测试与提交

### 4.1 提交前必做
1. `node --check` 校验改动的 `.cjs`。
2. 重启 Mock（取 8080 PID → `Stop-Process` → 后台 `node mock-server.cjs`）。
3. 跑 `verify-integrity.cjs`、`verify-authz.cjs`、`verify-supply-distribution.cjs`。
4. `frontend/admin` 与 `frontend/h5` 执行 `npm run build`。
5. 涉及新功能时同步更新 `docs/功能验收标准.md` 与 `test-results/guides/index.html`。

### 4.2 提交信息
- 格式：`type(scope): 简述`，type ∈ feat/fix/refactor/docs/test/chore。
- 一个提交只做一件事；修复 Bug 需在描述中写明复现路径与影响面。

### 4.3 代码审查清单
- [ ] 是否新增魔法数字/硬编码域名？
- [ ] 是否遗漏权限或数据范围校验？
- [ ] 金额是否用分计算？是否有浮点误差？
- [ ] 状态流转是否可跳步/可重复？
- [ ] 是否破坏既有回归（153 项供应链分销、40+ 完整性）？
- [ ] 列表是否兼容 current/size 并返回 total？
- [ ] 新增菜单是否同步 `menuPermissions` 与 `roleMenus`？

## 5. 重构评估

### 5.1 现状评分
| 维度 | 评分（5 分制） | 说明 |
| --- | --- | --- |
| 分层清晰度 | 4 | 服务层已抽取，但部分路由仍含业务规则。 |
| 一致性 | 4 | 响应、分页、鉴权风格统一。 |
| 可测试性 | 3.5 | 有回归脚本，但以接口级为主，缺单元测试。 |
| 规模控制 | 3 | `routes-admin.cjs`、`routes-core.cjs`、`seed-extra.cjs` 偏大。 |
| 类型安全 | 2.5 | Mock 为纯 JS；管理端有 TS 但接口类型多为 `any`。 |
| 配置化 | 3.5 | 分享域名已环境化；费率、结算周期已配置化。 |
| 综合 | **3.5 / 5** | 原型阶段可用，具备继续演进基础。 |

### 5.2 主要问题
| 优先级 | 问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| P0 | 无自动化单元测试，仅接口回归 | 重构回归成本高 | 为 service 层补最小单测（Node test runner）。 |
| P1 | `routes-admin.cjs`、`routes-core.cjs` 体积大、职责多 | 维护与冲突成本高 | 按域拆分：product/order/pay/supply/finance。 |
| P1 | 前端接口类型 `any` 较多 | 字段变更难发现 | 抽 `src/types/api.ts`，页面逐步替换。 |
| P2 | 部分规则在路由与 service 重复 | 口径不一致风险 | 规则只留 service，路由仅编排。 |
| P2 | 硬编码字符串（状态文案、渠道） | 多语言/扩展困难 | 抽常量与字典模块。 |
| P2 | Mock 与真实接口契约未固化 | 上真实后端易返工 | 用 OpenAPI/接口快照固化契约。 |

### 5.3 结论：暂不做“大爆炸式”重构
- 当前系统为可运行原型，模块边界基本清晰，回归覆盖关键资金/库存/状态链路。
- 大规模重写收益低、风险高，容易破坏 153 项供应链分销回归。
- 建议采用**渐进式重构**：只在新需求触达的模块内顺手拆分，保持接口与状态码不变。

### 5.4 渐进式路线
1. **第 1 步（低风险）**：为 `stock/fund/distribution/promotion/invoice/finance` 六个 service 补单元测试；抽出 `constants.cjs` 统一状态与文案。
2. **第 2 步（中风险）**：拆分 `routes-admin.cjs` 为 `routes-product.cjs`、`routes-order.cjs`、`routes-pay.cjs`，按原路由前缀注册，行为不变。
3. **第 3 步（中风险）**：管理端抽 `types/api.ts` 与通用 `useList`、`useDialog` 组合式函数，减少重复样板。
4. **第 4 步（按需）**：引入接口契约文件（OpenAPI），Mock 与真实后端共用；再评估是否替换 Mock。

### 5.5 不重构的红线
- 采购状态码 `0/1/2/3` 与流转顺序不可变。
- 资金流水类型与 direction 语义不可变。
- 权限码与菜单 id 不可随意调整（角色菜单依赖）。
- 接口路径与返回结构保持向后兼容，新增字段优先。
