# 福礼社平台架构评审报告

## 一、总体评价

### 1.1 优点

- **架构分层清晰**：基础设施层→技术中台层→业务中台层→应用接入层，四层架构符合微服务最佳实践
- **业务域划分合理**：商品域、交易域、卡券域、账户域、履约域、营销域、数据域，边界清晰
- **多租户考虑周全**：同时支持逻辑隔离和物理隔离，覆盖中小企业和央企两种场景
- **安全合规意识强**：五大账户独立记账、资金安全、合规审计等考虑到位
- **技术选型主流**：Spring Cloud Alibaba + Vue 3 生态，社区活跃，人才储备充足

### 1.2 总体风险评级

**中低风险**，整体架构设计合理，但部分细节需要优化。

## 二、技术架构评审

### 2.1 微服务拆分评审

| 服务模块 | 合理性 | 问题与建议 |
| :--- | :--- | :--- |
| 用户中心 | 合理 | - |
| 租户管理中心 | 合理 | 建议与用户中心合并为 `用户租户服务`，减少跨服务调用 |
| 商品中心 | 合理 | - |
| 卡券中心 | 合理 | - |
| 订单中心 | 合理 | - |
| 支付/结算中心 | 需拆分 | **建议拆分为支付中心 + 结算中心**，支付是交易链路核心，结算是财务侧，职责不同 |
| 五大账户中心 | 合理 | 建议独立为 `账户服务`，统一账务模型 |
| 批量处理引擎 | 需合并 | 建议作为基础组件，不作为独立服务 |
| 福利规则引擎 | 合理 | - |
| 供应链中心 | 合理 | MVP阶段可后置 |
| 履约/物流中心 | 合理 | MVP阶段可后置 |
| 营销/内容中心 | 需拆分 | 建议拆分为营销中心 + 内容中心，内容偏运营配置 |
| 消息中心 | 合理 | 建议作为基础组件 |
| 数据分析中心 | 合理 | MVP阶段可简化 |
| 合规审计中心 | 合理 | 建议独立审计日志组件，各服务统一接入 |
| AI智能中心 | 合理 | MVP阶段可后置 |

**优化建议**：MVP阶段建议精简为以下8个核心服务：

```
1. 用户租户服务 (user-service)       - 用户、租户、组织架构、权限
2. 商品服务 (product-service)         - 商品、分类、库存、品牌
3. 卡券服务 (coupon-service)          - 福利卡生成、发放、绑定、兑换
4. 订单服务 (order-service)           - 订单、购物车、履约调度
5. 支付服务 (payment-service)         - 多渠道支付、对账
6. 账户服务 (account-service)         - 五大账户、资金安全
7. 消息服务 (message-service)         - 短信、邮件、推送、站内信
8. 网关服务 (gateway-service)         - API网关、鉴权、限流
```

### 2.2 技术选型评审

#### 后端技术栈

| 组件 | 选型 | 评价 | 建议 |
| :--- | :--- | :--- | :--- |
| 微服务框架 | Spring Boot 3.x + Spring Cloud 2022.x | 合理 | 确认使用 Spring Cloud Alibaba 版本 |
| 服务注册/配置 | Nacos | 合理 | 建议使用 Nacos 2.x，性能提升明显 |
| API网关 | Spring Cloud Gateway | 合理 | - |
| RPC通信 | Dubbo / OpenFeign | 需明确 | **建议统一使用 OpenFeign**，HTTP 协议更利于调试和监控 |
| 分布式事务 | Seata | 合理 | MVP阶段可先不用，用本地事务+消息最终一致 |
| 消息队列 | RocketMQ | 合理 | - |
| 分布式锁 | Redisson | 合理 | - |
| 缓存 | Redis 7.0 集群 | 合理 | - |

#### 数据存储

| 组件 | 选型 | 评价 | 建议 |
| :--- | :--- | :--- | :--- |
| 主数据库 | MySQL 8.0 + ShardingSphere | 合理 | MVP阶段可先不分库分表，单库即可 |
| 搜索引擎 | Elasticsearch | 合理 | MVP阶段可先用 MySQL LIKE + 索引 |
| 对象存储 | 阿里云OSS / MinIO | 合理 | - |
| 数据仓库 | ClickHouse | 合理 | MVP阶段可后置 |

**优化建议**：
1. **RPC通信统一为 OpenFeign**，避免同时维护两套RPC框架
2. **MVP阶段简化数据架构**：单库 MySQL + Redis，不急于分库分表
3. **分布式事务 MVP阶段暂不引入 Seata**，使用本地事务 + 消息队列 + 定时补偿实现最终一致性

## 三、业务架构评审

### 3.1 多租户架构

**现状**：逻辑隔离（tenant_id）+ 物理隔离（独立数据库）

**优化建议**：
1. **推荐使用 Schema 隔离**（介于逻辑隔离和物理隔离之间）
   - 每个租户一个 Schema，数据隔离性好
   - 比独立数据库更节省资源
   - 迁移和备份更方便

2. **统一多租户实现**：使用 MyBatis-Plus 多租户插件 + 动态数据源
   - SaaS版：共享数据库，tenant_id 隔离
   - 企业版：共享数据库实例，Schema 隔离
   - 私有化版：独立数据库实例

### 3.2 五大账户体系

**现状**：福利卡额度/餐补/劳保/积分/健康 五个独立账户

**优化建议**：
1. **统一账户模型**：使用账户类型区分，而非五套独立表
   ```
   account（账户主表）
     - account_id
     - user_id
     - tenant_id
     - account_type (WELFARE_CARD/MEAL_SUBSIDY/LABOR_PROTECTION/POINTS/HEALTH)
     - balance
     - frozen_amount
     - status
   ```

2. **统一账务流水**：所有账户变动记录同一张流水表，便于审计和对账

### 3.3 卡券系统

**现状**：定额卡、权益卡、组合卡三种类型

**优化建议**：
1. **卡券模板 + 卡券实例** 分离设计
   - 卡券模板：定义卡类型、面值、有效期规则、适用商品等
   - 卡券实例：具体的一张卡，有卡号、密码、状态、持有人

2. **组合卡实现**：建议组合卡 = 多张子卡的集合，而非独立卡类型，更灵活

## 四、安全架构评审

### 4.1 身份认证

**现状**：OAuth2 + JWT + SSO

**优化建议**：
1. **建议使用 Spring Authorization Server** 作为统一认证服务
2. **Token 方案**：
   - Access Token：JWT，有效期 2 小时
   - Refresh Token：Redis 存储，有效期 7 天
   - 支持 Token 主动失效（登出、封禁）

### 4.2 数据安全

**补充建议**：
1. **敏感字段加密**：手机号、身份证、银行卡号等使用 AES 加密存储
2. **数据脱敏**：接口返回时敏感信息脱敏展示
3. **SQL 注入防护**：MyBatis-Plus + 参数化查询
4. **XSS 防护**：前端统一转义 + 后端输入校验

## 五、高可用与性能评审

### 5.1 并发指标

| 指标 | 目标值 | 可行性 | 建议 |
| :--- | :--- | :--- | :--- |
| 系统可用性 | ≥ 99.95% | 可行 | 多可用区部署 + 自动故障转移 |
| 页面响应 | ≤ 300ms | 可行 | CDN + 缓存 + 接口优化 |
| 订单并发 | ≥ 3000 笔/秒 | 需验证 | 需压测验证，建议分阶段目标：MVP 500 TPS |

### 5.2 优化建议

1. **多级缓存策略**：
   - 一级缓存：本地缓存（Caffeine）- 商品详情、配置信息
   - 二级缓存：Redis - 用户信息、库存、热点数据
   - 三级缓存：CDN - 静态资源、商品图片

2. **数据库优化**：
   - 读写分离（主从复制）
   - 热点数据缓存
   - 慢 SQL 监控

## 六、MVP 版本裁剪建议

### 6.1 MVP 必做功能

| 模块 | 必做功能 | 裁剪说明 |
| :--- | :--- | :--- |
| 用户租户 | 企业注册、员工管理、角色权限、登录认证 | 暂不做 SSO 对接 |
| 商品中心 | 商品管理、分类、SKU、库存、上下架 | 暂不做生态商品池、智能选品 |
| 卡券中心 | 定额卡生成、发放、绑定、兑换 | 暂不做权益卡、组合卡 |
| 订单中心 | 购物车、下单、订单状态流转 | 暂不做售后、订单拆分 |
| 支付中心 | 微信支付、福利卡支付 | 暂不做支付宝、余额支付 |
| 账户中心 | 福利卡账户、流水 | 暂不做其他四个账户 |
| 管理后台 | 基础配置、商品管理、卡券管理、订单管理 | 暂不做数据报表 |
| H5商城 | 商品浏览、搜索、加购、下单、支付 | 基础功能 |

### 6.2 MVP 技术简化

| 组件 | MVP方案 | 后期升级 |
| :--- | :--- | :--- |
| 数据库 | 单库 MySQL | ShardingSphere 分库分表 |
| 搜索 | MySQL LIKE + 索引 | Elasticsearch |
| 分布式事务 | 本地事务 + 消息补偿 | Seata |
| 服务数量 | 8个核心服务 | 逐步拆分细化 |
| 部署方式 | 单机 Docker Compose | Kubernetes |

## 八、总结与建议

### 8.1 核心结论

1. **整体架构设计合理**，业务域划分清晰，技术选型主流
2. **MVP阶段需要精简**，服务数量和功能都需要裁剪
3. **建议分阶段建设**，先跑通核心链路，再逐步完善

### 8.2 关键行动项

| 优先级 | 事项 | 说明 |
| :--- | :--- | :--- |
| P0 | 统一技术选型 | OpenFeign替代Dubbo，MVP暂不引入Seata |
| P0 | MVP服务裁剪 | 从16个服务精简到8个核心服务 |
| P0 | 数据库设计 | 基于统一账户模型设计核心表结构 |
| P1 | 多租户方案 | 确定隔离策略，实现MyBatis-Plus多租户 |
| P1 | 项目脚手架 | 搭建前后端基础框架 |
| P2 | 性能规划 | 分阶段性能目标，逐步优化 |
